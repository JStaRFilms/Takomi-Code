## Persistence and delivery

Authored submissions use one typed `pi.input-submission` activity with a stable thread/request identity and null turn ID. Record and resolve events preserve immutable content, creation time and original sequence. Direct durable lookup bypasses the retained 500 activities. Validation precedes receipt deduplication; conflicting content or terminal outcomes cannot appear accepted. No table or migration was added.

The history stores original text, normalized image/file references and structured context. Expanded host-path prompts, inline image bytes and raw native errors stay out of persistence. Revert/bootstrap cleanup retains referenced attachments, and thread deletion removes them. Shared reduction and pagination update the original row rather than inserting a second one.

`provider.submitPiQueuedInput` requires operate scope. Its request-ID/sequence response confirms durable recording only. Canonical SHA-256 fingerprints and durable receipts prevent duplicate record events, copies or native execution. The existing Normalizer and provider-text preparation serve ordinary turns too. Native preparation preserves all context or rejects it, rather than silently truncating it.

The server captures the original wrapper, binding, context, process generation, supported launch version and B05 lease before attachment preparation. It stages the captured operation before recording. Preparation and failed-record cleanup distinguish definite failure, durable retention and uncertain commit. The existing hot reactor delivers only new record events. It never replays startup history, recovers a provider or uses the ordinary send queue. One pending slot lasts through durable resolution. Reactor drains include active inputs; the settled test receipt follows resolution persistence. Persistence failure leaves unconfirmed without retry or a false receipt.

Native delivery uses `steer` or `follow_up`, full native image blocks and expanded context. All yielding preparation, routing, filesystem and liveness checks finish before the final synchronous original-context/version/lease proof and admission to original stdin. The correlated Deferred exists first. The existing 30-second deadline and JSONL cap are unchanged. Admission is the uncertainty boundary. Later cancellation, loss, replacement, timeout or write failure becomes unknown unless a valid correlated acknowledgment already established an outcome. Known acceptance remains authoritative after owner retirement.

No ordinary user message, fake turn, checkpoint, title input, pendingPrompt, model/settings write or independent-work settlement is created.

## Clients and draft consumption

The actual web ChatView/ChatComposer and mobile use-thread-composer-state/ThreadComposer paths prepare the existing composer content. Web reuses start/await/get uploaded attachments and message-context construction. Mobile reuses prepareTurnAttachments and persists upload references while remapping context bindings. Neither route enters the ordinary send, local waiting-draft or mobile outbox paths. Desktop inherits web. No new keyboard, palette or Settings write was added; existing Send and alternate-send entrypoints retain their behavior.

The shared runtime uses the current session owner, supported capability, extension generation and captured connected RPC transport, including connection generation. A scoped hot subscription is installed before submission. Confirmation comes from matching typed live events, never a 500-activity scan, polling or reconnect replay. Recording and native acceptance are separate states. Unconfirmed remains pending for at most 60 seconds after the durable-recording response. The fixed local window does not change native or RPC deadlines. Expiry releases only that request's local slot and drops its draft callback, while history remains unconfirmed and the draft stays. Timers stop on terminal outcomes, source changes, disconnect, unmount or disposal. Late terminal events can update the last confirmed record without consuming its expired callback or overwriting a newer pending request. Listener termination invalidates callbacks and releases local pending state without replaying anything. Late RPC success or failure cannot overwrite a newer pending request or erase a known terminal result.

Only queued or handled confirmation may call the originating draft guard. Guards compare current source identity, editor identity and revision, text, authored attachments/context and draft revision. Web uses the real Tiptap document revision and File identity; mobile uses native eventCount and navigation focus. Edit-and-undo, ordinary Send followed by replacement text, attachment/context changes, editor replacement, navigation away/back, disconnect/reconnect and owner/generation changes invalidate consumption. Own upload-ID/environment stamps do not count as edits. Other-device events never hold a local consumption callback. Guards also revalidate after asynchronous attachment preparation, before dispatch.

Both timelines decode typed submissions and show intent, recoverable text, images/files/context and outcome in separate rows. Web excludes them from tool/activity grouping and preserves them through folded-turn handling. Mobile isolates them from grouped work logs and uses existing authenticated attachment previews and context markdown. Unknown or malformed typed payloads do not gain submission authority. Queued means acceptance, not current membership or idle execution. Handled does not mean model work completed. Explicit resubmission warns about duplicate work; there is no automatic Retry or model spinner.

Read-only authorization is enforced and tested at the authenticated RPC. Clients do not invent a separate scope-discovery API or claim authority from a visible button.
