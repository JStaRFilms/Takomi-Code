# A02 extension projection architecture

Parent synthesis of the synchronous architect return. No architect files/tests/builds/clients were run. The source-grounded recommendation is selected for implementation; exact type/export names and service wiring must follow actual repository conventions, not guessed APIs.

## Selected paths

Use bounded ephemeral current state for status, string widgets, runtime subtitle and editor suggestions. Use existing durable work-log activities for notification severity and correlated B02 command outcomes. Avoid writing every widget refresh into event sourcing or deriving current state from a bounded historical activity window.

Native sources: Pi 0.99.1 RpcExtensionUIRequest declares setStatus/statusKey/statusText, setWidget/widgetKey/widgetLines/widgetPlacement, setTitle/title and set_editor_text/text. Canonical runtime already publishes serializable widgets/title; OAuth-router chooses string-array reports outside TUI mode. No suite bridge is needed for those supported methods. Arbitrary TUI factories/custom components remain native-limited.

Current T3 activity upsert can bound projection rows but not underlying event growth. The 500-activity detail window cannot recover unchanged status after enough unrelated activity. Codex thread metadata renames the T3 thread and is not a subtitle interface. Existing auth snapshot-first subscriptions are the nearest reusable transport pattern.

## Data flow and source boundaries

PiAdapter validates/normalizes native UI fields and emits typed provider extension-state begin/update/end events without raw native record payload. ProviderService forwards through its current stream. The serialized ingestion worker routes extension-state events to an ephemeral keyed service before durable activity/lifecycle persistence. An authorized snapshot-first streaming RPC delivers current state to shared environment/thread-scoped client state. Web/desktop and native mobile use existing composer/feed/detail primitives.

Notifications and B02 outcomes continue through existing persisted activities/projectors. Preserve existing categories and original pending.turnId; no fabricated assistant messages or generic runtime.error that changes model-run state.

Files to inspect/extend: contracts providerRuntime.ts/rpc.ts/server.ts and exports; PiAdapter; ProviderRuntimeIngestion and service layering; ws.ts and auth/RpcAuthorization; client-runtime RPC/subscription tags and shared thread state; web session-logic/ChatView/MessagesTimeline/composer drafts; mobile threadActivity/work-log/ThreadComposer/feed/drafts. Parent authorizes only bounded slices of this graph. Persistent schema/migration is not needed for the selected ephemeral path.

## Snapshot and lifecycle rules

Snapshot identifies thread, owning provider instance, opaque process-generation token, revision, active/inactive state and update time. Contains exact-key status entries, exact-key widgets with placement, nullable runtime subtitle, nullable latest editor suggestion ID/text, truncation and bounded overflow signal. Environment is authenticated connection scope, not a provider-supplied remote identifier. Clients subscribe using ScopedThreadRef. Resolve owner instance server-side.

Use Map/arrays, not arbitrary-key objects. Keys preserve identity; reject overlong keys, never trim/truncate them into collisions. Existing Pi request-ID bounds are 256 code points/512 UTF-8 bytes. Suggested shared bounds: 32 statuses, 16 widgets, 100 lines/widget, 2 KiB/line, 16 KiB status text, existing 4096-code-point/16 KiB title, existing 512 KiB editor prefill, 128 KiB aggregate status/widget/subtitle text. Editor suggestion is separately bounded. Use Unicode-safe truncation and serialized UTF-8 accounting; expose truncation. New keys at capacity signal overflow while existing replacements/clears still work. Omitted status/widget content clears; empty text/arrays are valid. Placement defaults aboveEditor. Strip terminal escape/control sequences while retaining meaningful line breaks; render text only.

Emit begin before startup output can be processed, not only after session.started or an active turn. Old generation output remains fenced. End/replacement clears ephemeral state; settlement of a model turn does not. A server restart intentionally loses the terminated owner's state, and the new owner republishes. Snapshot first/reconnect must be atomic with updates. Delete thread/end releases state; memory is bounded by actual live contexts, not every thread ever visited. Suppress identical updates.

Backpressure requirement added by parent: snapshot subscriptions must be latest-state/coalescing and bounded under slow remote consumers. SubscriptionRef.changes alone must not introduce an unbounded queue of large snapshots. Reuse current bounded transport patterns and prove a slow consumer cannot accumulate unbounded state; no polling-only synchronization.

## Draft/title/private behavior

Runtime title is only a subtitle, never native name/manual thread title/global Electron title. Native editor updates have no request ID or draft revision, and current turn-start contracts do not propagate initiating-client revision. Therefore use suggestions only. Explicit local Replace/Insert/Dismiss is safe; no automatic draft replacement or auto-send. Confirm against the captured current draft/revision, preserve attachments/metadata, and require new confirmation if the local draft changed. Dismiss is local per suggestion ID. Other devices' drafts stay untouched.

Vault private input/archive/one-use transfer stays on existing private paths. State snapshots and notices never receive private response values. Do not broaden raw native logging.

Additional producer-side privacy blocker: oauth-router/oauth-flow.ts emits authorization URLs/device codes through ordinary notify with no private/owner metadata. Generic notify cannot be claimed secret-safe. Do not add auto-opening links, OS notification delivery or publishing. Later private OAuth parity requires an owner-aware producer contract like existing provider-auth handling; it is not part of ordinary widget/severity projection.

## Durable notification and command outcomes

Add optional severity info/warning/error to RuntimeWarningPayload, preserving old provider defaults. Pi maps native notifyType; missing defaults to info. Keep runtime.warning transport because runtime.error affects model/session lifecycle. Ingestion maps error severity to existing error activity tone and retains warning severity in payload without a database-tone migration.

Typed optional command-outcome metadata carries B02 requestId, handled/failed outcome and optional commandName, not arguments. Retain detail.kind compatibility. Handled is info, failed is error, and original pending.turnId remains authoritative. Unknown native notices remain uncorrelated extension notices. Preserve Vault categories/transfer handling and dedicated UI rather than duplicating private content in generic rows.

Web session-logic/MessagesTimeline and mobile threadActivity/work-log currently infer warning appearance from runtime.warning. Prefer explicit severity for new Pi events and retain legacy fallback for old events/providers. Shared work-log helpers are the preferred source for interpretation. Failed command results need a visible failed label and no fabricated assistant text/checkpoint controls.

## Required proof

Backend: exact keys/collisions, replace/clear/empty values/placement, ANSI removal and shared bounds, idle startup updates, identical-update suppression, atomic snapshot/reconnect, stale generation/deletion/auth denial and bounded slow consumers. Assert no persisted activities from ephemeral updates.

Client: desktop publishes and phone reconnects to same current state; local hide does not clear another device; process replacement clears old state but manual names/drafts persist; A failure stays with A while B is running; competing drafts are only changed by explicit confirmed local editor actions. Native/widget functionality and real client proof are distinct.

Runtime suite compatibility, private OAuth ownership and actual web/installed-desktop/mobile device/tool verification remain open. No architecture/source check counts as integrated proof.
