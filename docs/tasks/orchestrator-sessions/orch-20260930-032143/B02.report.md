## Root cause and native evidence

The adapter allocated an active turn when sending prompt, ignored general prompt dispositions, and settled successful command acknowledgements only for a tracked Vault prompt. A handled general extension command or consumed non-slash input therefore had no completion path when Pi did not run an agent. Conversely, treating every handled acknowledgement as completion would terminate independently started work.

Read in full from the installed Pi 0.99.1 package at `C:/Users/johno/AppData/Roaming/npm/node_modules/@earendil-works/pi-coding-agent`: docs/rpc.md, docs/rpc-commands.md, and docs/json.md. Read relevant implementation in dist/modes/rpc/rpc-mode.js and dist/core/agent-session.js, plus canonical takomi-runtime/commands.ts. No native process or extension session was launched for that investigation.

Native ordering:

- rpc-mode.js:298-317 calls prompt immediately and emits the response from its preflightResult callback. Only rejection before preflight generates a failed response.
- agent-session.js:1449-1566 executes extension commands before input handling and streaming queue admission. Command or input-handler consumption calls preflightResult with handled. Ordinary prompt calls started before running the agent; streaming admission calls queued.
- agent-session.js:1568-1592 catches a command-handler exception, emits extension_error with event command and extensionPath `command:<name>`, and still returns handled.
- agent-session.js:1780-1807 implements sendUserMessage through an asynchronous prompt. The extension API at 2644-2651 starts it without awaiting it and reports asynchronous failure separately as event send_user_message, path `<runtime>`. This notice carries no prompt ID and cannot safely be assigned to a submitted command.
- Canonical takomi-runtime/commands.ts:230-231 sends routing review through pi.sendUserMessage without awaiting the run. Its status handler at 308-312 only notifies. Native work may therefore start before or after the outer command acknowledgement.
- agent_settled, not agent_end, ends automatic work. Native settlement also precedes deferred settled actions, which can start another run.

A search of the installed dist JavaScript found no extension_command_error event. This implementation uses the actual extension_error record and its available correlation fields, not an invented event or request-ID field.

## State and projection decision

Added one bounded pending-prompt map and one native-run-active flag. The map stores generated prompt ID, turn ID, ownership of the original turn, optional command name, and an associated failure. It does not retain prompt text, command arguments, private input, or transfer material. Admission stops at 100 unacknowledged prompts instead of evicting live correlation. Response handling consumes IDs once. Stop, replacement, and process exit clear the map and private pending state.

A handled or rejected submission produces an existing runtime.warning work-log notice with `detail.kind = pi.prompt-outcome`, request identity, outcome, and optional command name. No synthetic assistant message is emitted. A command submitted during a native run settles this acknowledgement independently and keeps the existing turn ID, run, and session status. Ordinary steering still uses streamingBehavior steer and waits for native settlement. A second concurrent durable turn is not introduced.

For an idle handled input, completion closes its original submission once unless agent_start has already established native work. If a run is already active, acknowledgement cannot terminate it. If agent_start arrives after the submission completed, it allocates a fresh canonical turn ID before text and tools are mapped. A run that finishes before acknowledgement remains terminal; that acknowledgement cannot reopen it or close a later turn.

Associated handler failure overrides handled. Command-name correlation applies only when exactly one outstanding submission matches the native event command and `command:<name>` path. Overlapping same-name submissions and input/runtime notices remain extension notices. Rejection during another run does not set that run's failure. Uncorrelated extension notices use runtime.warning because runtime.error currently changes ingestion's session to error and would incorrectly settle unrelated active work.

Existing T3 behavior supports the fresh turn ID:

- ProviderAdapter.sendTurn and ProviderService forward canonical lifecycle events; Pi's resume cursor is the same persistent session file for independent work.
- ProviderRuntimeIngestion accepts turn.started without a pending user start when no other turn is active, then maps it to thread.session.set with running status and the new ID.
- The decider accepts that session update. Projector and ProjectionPipeline create a new running turn and preserve the completed submission record. Reusing a terminal ID would not be a valid representation.
- The added ingestion test proves this with receipt/enqueue and worker drains, including assistant text, a tool activity, a failed mid-run command notice that leaves the run active, and final settlement of both distinct records.

No authoritative state query can rule out arbitrarily later extension work. The fix follows native start/settlement events instead of adding a query-based guess or grace-period timer.

Replacement testing exposed an existing in-scope gap: stopContext with emitExit false stopped an old active generation without a turn terminal event. Teardown now settles an active turn once regardless of whether a session-exited notice is requested. It fences output before cancelling UI, so cancellation-triggered buffered work cannot revive the old owner. completeTurn claims the active ID before yielding to competing terminal paths. Existing interruption timing was not changed; no sleep was added to implementation or tests.

## Scoped revision after R02

Read R02.review.md and B02.revision.md in the same writer conversation. Corrected only their two confirmed defects. The original verification above records the initial implementation, not acceptance of the reviewed defects.

### Originating turn ownership

A pending async command can outlive its independent native run. Both its matched extension-error notice and its later prompt-outcome notice inherited eventBase's current active turn, assigning A's failure to B's work log. They now override association with the matched pending.turnId. Reporting a late failure does not reopen A or modify B's lifecycle.

The controlled process test starts and settles A's native work while withholding A's acknowledgement, starts B, then releases A's error and handled acknowledgement through an explicit peer control. It checks both notices belong to A, B remains running, and each turn completes once. Corrected duplicate acknowledgements cannot reclassify the failure.

The new ingestion test separately feeds those canonical notice shapes through the existing enqueue/drain path. It checks both persisted activities belong to completed A, B's persisted turn and session remain running, and A's complete record is unchanged through the notices and B's eventual completion. This is persisted ownership proof, not a claim of a single end-to-end adapter-plus-ingestion test.

### Explicit invalid disposition

Previously an invalid explicit disposition consumed its pending ID without any outcome or settlement. Corrected acknowledgements were then ignored, stranding idle work. Validation now precedes consumption. Valid started, queued, and handled values are unchanged. An absent data field or a record without a disposition field retains the legacy path. Explicit invalid disposition strings, nulls, objects, or malformed data shapes produce the fixed message `Pi returned an invalid prompt disposition.` and one correlated failed outcome. The malformed wire value is not copied into new canonical events or synthetic text.

The invalid acknowledgement consumes its ID once as a protocol failure. An idle owning submission settles failed deterministically. During unrelated native work it settles only its submission outcome; that run continues to its actual native settlement. Corrected and contradictory duplicates cannot turn the outcome into success. The existing native diagnostic logger's raw-record policy was not changed.

Ten controlled cases cover five invalid shapes with and without unrelated native work. A further case checks a legacy absent disposition retains its established behavior. Every absence check follows the peer's drain receipt; no sleeps or polling were added. All existing valid, Vault, private-input, replay, generation, and transfer tests remain intact and pass.
