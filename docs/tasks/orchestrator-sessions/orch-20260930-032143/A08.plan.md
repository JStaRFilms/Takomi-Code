# A08 native control plan

The second report corrects the stock-RPC idle-only assumption in the first. Ship read-only stats first. Manual compaction requires an approved native atomic-ownership change. No checks or native operations were run by the architect.

## Recommendation

Split B08 into two bounded slices:

1. **B08a: native manual compaction and truthful compaction lifecycle.**
2. **B08b: native session statistics through an authenticated read RPC.**

Compaction changes orchestration ownership. Stats need a separate read contract and request-driven client state. Combining them into a generic native-controls framework would add machinery neither feature needs.

Reuse the existing context meter, composer command menu, palette, work log, dialogs and mobile sheets. Add only an optional-instructions dialog and session-stat details where no existing control provides them. Desktop continues to use web.

No files changed or checks executed.

## Source findings that constrain implementation

- Installed Pi is **0.99.1**. Its public RPC docs, compaction docs, event docs, session docs, RPC UI docs and native implementation establish the semantics below. The repository also contains a **0.84.4 replay fixture**. Those are different evidence sources, not proof that either runtime has passed integrated verification.
- `ProviderCompaction` already distinguishes native compaction from slash-command compaction. `PiAdapter` currently exposes neither.
- Generic compaction currently enters through `thread.turn.start` containing `/compact`. Web creates an optimistic user message; orchestration persists a message and pending turn. This avoids sending the prompt for native adapters, but still invents a T3 conversation turn. Do not use that route for the new Pi control.
- `ProviderService` presently attributes a native compacted event to its pending request and can settle that request from unrelated `turn.completed`, `turn.aborted` or `runtime.error` events.
- Pi compaction events **have no command ID**. The `compact` response repeats the RPC ID and is authoritative for that submitted operation.
- Native `compact(customInstructions)` first calls `abort()`. It can interrupt independently running work. Keep the GUI operation idle-only and enforce that at the adapter, not merely in the button.
- Native hooks can veto, provide custom compaction content, request UI or fail. Pi emits `compaction_end` before returning its correlated response.
- Current Pi failure detection checks `result === null`. Current Pi omits `result` on failure. Aborted compaction also currently receives an item status of `completed`.
- Pi's current `interruptTurn` requires an active turn and terminates the process after a grace period. It cannot cancel idle manual compaction as written.
- `get_session_stats` aggregates **all session entries**, including abandoned branches, usage entries, tool-reported usage and summarization usage. It is not active-branch usage, current context or account quota.
- Native context is an estimate. Immediately after compaction its token count and percentage are null until valid post-compaction assistant usage exists.
- Web's context derivation skips invalid usage and searches backwards. Its formatter prints null as `"0"`. Both would misrepresent an unknown post-compaction context.
- There is no dedicated compact action in the current command palette or keybinding contract. Mobile currently derives compaction from `/compact` messages rather than a native-control lifecycle.

## B08a implementation contract

### Command and lifecycle

Add a narrow orchestration command:

```text
thread.compaction.start
  commandId
  threadId
  expectedProviderInstanceId
  customInstructions?
  createdAt
```

Add the matching `thread.compaction-requested` intent. It must not emit `thread.message-sent`, `thread.turn-start-requested`, create a turn, generate a title or trigger a checkpoint.

Use existing thread activities for requested, running and terminal presentation. Each activity carries:

```text
requestId = commandId
providerInstanceId
status = requested | running | completed | cancelled | failed | interrupted
bounded safe error code/detail when applicable
```

Record instructions only in the necessary command payload, not redundantly in activity details, telemetry or native logs. Preserve multiline text exactly. Apply a documented UTF-8 bound before enqueueing, for example 16 KiB.

Add `thread.compaction.cancel` targeting the original request ID and expected owner. Cancellation must never target whichever operation happens to be active later.

The dispatch receipt proves command acceptance, not compaction completion. Clients settle from the matching terminal activity.

### Reuse `ProviderCompaction`

Extend its native variant minimally:

- Optional `completion: "response"`. Omission retains existing event-driven behavior.
- Optional operation options carrying `customInstructions` and request identity.
- Optional request-targeted native cancellation.

Pi uses response-driven completion. Codex and OpenCode retain their existing event-driven contracts. Existing slash-command adapters remain unchanged. Do not silently accept instructions for an adapter that cannot preserve them.

For response-driven operations, retain the service's concurrency claim and deadline, but do not settle or retag the request from unrelated runtime events. Await the adapter's correlated completion directly.

This distinction is necessary because Pi events lack request IDs. Do not guess correlation from event order, `reason: "manual"` or current turn ID.

### Adapter behavior

In `PiAdapter.ts`:

1. Capture the exact context object, process generation and owning instance.
2. Claim one pending manual-compaction slot before yielding.
3. Reject stopped, replaced or fenced contexts, active native runs, pending prompt submissions, existing compaction and pending native input.
4. Read `get_state` once. Require idle state, no compaction and no queued native messages. Recheck local ownership and run state after the response.
5. Send only:

   ```text
   { id, type: "compact", customInstructions? }
   ```

6. Validate the matching response's ID, command, success and bounded result fields with schemas.
7. Settle once from that response or a confirmed cancellation/process-exit/deadline outcome.

The public control uses the **current native model and settings**. Do not apply a future composer model selection or introduce model selection in this dialog. Pi hooks and routing may choose how summarization actually runs.

Use a compaction-specific deadline compatible with the existing ten-minute service limit. The current fixed thirty-second `requestRpc` deadline is unsuitable. Pending-RPC cleanup belongs in an `ensuring` path, including interruption.

A request timeout does not prove native work stopped. Keep retry blocked until the original operation settles or the process is explicitly replaced. Do not turn timeout into “ready” and permit overlapping compaction.

### Native events and turn ownership

Keep native automatic compaction observations separate from the manual request lifecycle:

- Capture the originating turn at `compaction_start`.
- Use that captured turn for the matching observation, not `eventBase`'s current active turn.
- Manual control activities have no fabricated turn ID.
- A successful native end produces the existing compacted divider once.
- A correlated manual response produces the request's terminal activity, not a second divider.
- Uncorrelated native compaction events never satisfy or acquire the manual request ID.
- Missing result plus `aborted: true` means cancelled.
- Missing result without abort means failed.
- Failure and cancellation emit no successful compacted state.
- Successful automatic compaction does not finish the native run. Preserve overflow retry and B01 settlement behavior.

Do not pass native `summary`, `details`, first-kept entry IDs or raw event records into compaction activity details. Emit allowlisted numeric counts and explicit estimate provenance.

### Cancellation and hooks

For an owned idle manual compaction, use native `abort` through adapter RPC. Pi has no `abort_compaction` RPC.

Before sending abort, verify the request still owns this process and no independent run has taken over. Otherwise reject cancellation rather than abort someone else's work. Await native settlement. Do not call the existing turn-interrupt path or fabricate `turn.aborted`.

Leave ordinary Stop semantics unchanged. Process stop, replacement and deletion interrupt the pending operation and prevent later output from reviving its controls.

Keep existing extension UI transport available during compaction. Hook veto is cancellation, not success. Custom handler results may omit summarization usage. Cancelling a hook dialog is not itself proof the compaction was cancelled.

### Context presentation

Add optional provenance to compacted observations, sufficient to identify Pi's estimated post-compaction count and unknown current context.

For Pi, a successful compaction invalidates older context snapshots. The meter must show “Unknown until the next response”, not old usage or zero. Keep the compaction estimate in the divider/details, separately labeled.

Do not change every provider's numeric usage contract to nullable just to represent this. Make the client presentation explicitly nullable and recognize Pi's compaction invalidation boundary. B08b can supply a fresh native estimate without continuous reads.

## B08b stats contract

### Read RPC and DTO

Add `provider.getPiSessionStats` to `packages/contracts/src/rpc.ts`.

Input:

```text
threadId
expectedProviderInstanceId
```

Success:

```text
threadId
providerInstanceId
opaque process generation
fetchedAt
source: "pi-native"
scope: "all-session-entries"

messages:
  user, assistant, toolCalls, toolResults, total

tokens:
  input, output, cacheRead, cacheWrite, total

cost:
  amount
  currency: "USD"
  provenance: "native-reported"

contextUsage:
  null, or
  tokens: nonnegative integer | null
  contextWindow: positive integer
  percent: finite nonnegative number | null
  provenance: "native-estimate"
```

Missing context means unavailable. Null tokens mean unknown. Missing or malformed required native statistics fail the read rather than becoming fabricated zeros. Native zero cost remains zero, labeled reported cost, not proof of free billing or invoice accuracy.

Exclude `sessionFile`, raw model objects, credentials, summaries, arbitrary details and native session content. Native `sessionId` can remain server-side for identity checks.

## Approval choice

The meaningful behavior choice is whether manual compaction may interrupt a running agent.

**Recommend idle-only**, matching the current generic GUI restriction. Native Pi can abort the active operation before compacting, but silently doing that would violate independent-work ownership. Supporting “Stop current work and compact” would need a separately confirmed operation and belongs outside these slices.

The two small dialogs/sheets fit the already clarified permission for missing feature controls. No new visual system, arbitrary RPC gateway, native execution mechanism or Genesis reset is needed.

## Correction: stock RPC cannot guarantee idle-only compaction

My earlier reservation/recheck proposal does not close the child-process race.

Installed Pi 0.99.1, under `C:/Users/johno/AppData/Roaming/npm/node_modules/@earendil-works/pi-coding-agent/dist/`:

- `:627–630` awaits handling, writes the response, then awaits stdout backpressure.
- `:644–645` invokes each input handler without awaiting the previous handler.
- `core/agent-session.js:2100–2103` starts manual compaction with `await this.abort()` before setting its compaction controller.
- `:1841–1851` marks an active run aborted, aborts retry/compaction/branch summary, calls `agent.abort()`, then waits for idle.
- Nested `pi-agent-core/dist/agent.js:218–219` aborts whichever `activeRun` exists.

Conceptual reproduction:

1. Pi returns idle `get_state`.
2. An already accepted extension continuation starts independent native work.
3. T3 sends `compact`.
4. Pi aborts that independent run, then compacts.

`PiAdapter.ts:2272–2277` learns about work only when it consumes `agent_start`. That observation can arrive after compact is queued. Local reservations and post-response checks cannot undo the abort.

## Safe compaction requires an approved native change

No validated atomic compaction bridge appears in the inspected repository. `PiLaunchResources.ts:8–16,206–228` loads suite/companion extensions; it does not provide such a bridge. `packages/takomi-pi-host/src/` provides session utilities, not live atomic controls.

An extension doing `ctx.isIdle(); ctx.compact()` is **not sufficient**. `agent-session.js:2700–2712` forwards `ctx.compact` to the same asynchronous abort-first implementation, which yields before acquiring compaction ownership.

The smallest reliable change is a native conditional-compaction operation that synchronously checks and reserves execution before any await, rejects competing run admission, and supports operation-targeted cancellation. A versioned extension could expose it only if the native runtime supplies that ownership guarantee. A shared flag used by one extension cannot constrain unrelated native continuations.

This needs approval for native runtime/extension compatibility and delivery work. Do not introduce an arbitrary gateway or replace RPC with an SDK host. Keep compaction blocked meanwhile.

## Timeout and correlation requirements

For eventual compaction:

- Client/request timeout means outcome unknown, not cancellation.
- Keep the process/request slot occupied until its correlated terminal result or confirmed process exit.
- Stock `abort` acknowledges session idleness, not cancellation of a particular request. A delayed abort can hit replacement work.
- Pi compaction events lack request IDs. `ProviderService.ts:1181–1188` currently attributes compacted events and accepts unrelated turn/error terminals. That cannot prove manual completion.
- Use the correlated operation response for manual settlement. Preserve automatic observations separately; create no user message or T3 turn.
- A focused settled receipt may be added to `orchestration/Services/RuntimeReceiptBus.ts` when implementing the forked mutation. Stats need no receipt API. Tests should await controlled responses and worker drains, not polling.
