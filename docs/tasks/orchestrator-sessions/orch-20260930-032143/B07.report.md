## Delivered

The real web ChatComposer and native ThreadComposer now offer plaintext editor suggestions beside their editors, with explicit local Replace, Insert and Dismiss. Desktop inherits web. Applying always requires review of the current and proposed draft. Empty suggestions propose clearing text only. No action sends a turn, changes queues, calls a mutation RPC, renames anything or writes another device's draft.

I read the merged editor, draft, selection, metadata and extension-state APIs before implementation, along with AGENTS, unslop, D01, B05/B06 acceptance and report, M01 validation/review and G03 rescope. B05/B06 transport, support gates and presentation components were not modified. Upstream suggestion IDs, active-descendant accessibility and existing editor synchronization remain in place.

### Source and connection guards

Each request captures environment/thread, the actual native owner, process generation, suggestion ID and text, connection generation and a local authorization revision. Final Apply reads the scoped extension-state, owning thread shell and connection-state atoms again. It requires supported current extension state, an active matching native owner, a generation, a desired connected environment and a non-offline connection. Missing, unsupported, stopped, interrupted, errored, disconnected, replaced or navigating targets cannot authorize an old action. A future model selection does not substitute for a current native owner.

Subscriptions observe source, owner and connection transitions. Their monotonically increasing authorization revision fences an away-and-back transition even if the identical candidate returns. Supervisor generation also fences reconnects that occur before the extension snapshot changes. Disposing either composer binding invalidates its actions. Native navigation focus is checked at intent and Apply, with blur/focus listeners fencing pending review. Web actions require the actual server-thread draft target and honor the editor's approval, private-answer, responding and project-selection locks. Native actions honor context-import and dictation read-only locks.

Review is rendered only while its captured source remains current. A replacement source does not retarget an open review. Dismiss rechecks the exact offered source and authorization revision too.

### Draft, selection and metadata guards

Both adapters subscribe to the actual local draft store and increment a binding-local revision whenever that scoped draft object changes, including attachment and settings changes. This catches edit-away/edit-back changes, not just different strings. Request and Apply read the latest store text, revision, selection and editor state in the same JS turn. There is no await between the final reads and the text-only setter.

Web reads the real Tiptap `readSnapshot` and `readSelectionRange` APIs. Their range uses serialized text offsets, not DOM or collapsed-token offsets. Insert replaces that range or inserts at its caret. A mismatch between editor text and authoritative store text blocks an action until they agree. The existing Zustand `setPrompt` spreads the current draft, preserving files, images, terminal/context metadata, selected model, provider options and runtime modes.

The real-editor test caught a focus race: calling `focusAt` immediately after the store write could report the old editor text back through onChange. ChatComposer now flushes the controlled value/cursor update before invoking `focusAt`. This also avoids routing a suggestion through ordinary text-change attachment reconciliation.

Native iOS and Android handles expose their latest JS-acknowledged value, selection and native event count through the existing revision history. `readComposerNativeSnapshot` reads accepted native events ahead of a delayed React render. The action rejects a native/store text mismatch and rechecks native event count and selection before applying. Text and caret then travel together through the existing controlled-document revision guard. No asynchronous imperative native selection call follows the draft write. The generic non-native editor shim lacks that snapshot API and is honestly labeled Append to draft instead of Insert.

Mobile's ordinary `setComposerDraftText` can prune context-linked file attachments. Suggestions therefore use a narrow `setComposerDraftSuggestionText` setter that spreads the latest draft and changes only text. It does not prune attachments, context, share provenance, model/options or other metadata, including a context-only draft cleared to empty text. No persistence schema or metadata framework was added. Existing persistence sweeping and ordinary editing behavior remain unchanged.

If any draft revision, content, selection or native event revision changes during review, Apply writes nothing and offers a refreshed confirmation. Another change requires another confirmation. The store write never spreads the captured old draft over newer attachments or options.

### Bounds and local consumption

Apply uses the existing `PROVIDER_SEND_TURN_MAX_INPUT_CHARS` limit of 120,000 for both received text and the complete resulting draft. Nothing is silently clipped. The compact preview abbreviates to 120 characters, while existing disclosure/sheet patterns expose all received plaintext for selection and copying. Aggregate native truncation/overflow flags are separately labeled and conservatively block application because the DTO cannot identify whether the suggestion itself was shortened.

Dismiss and successful application consume only the exact environment/thread/owner/process/suggestion identity on this client. Unrelated status updates do not reoffer it. A new candidate or process can be offered. Storage holds one current identity per thread, capped at 64 thread entries, rather than a history of suggestion IDs. It is in-memory client state, not server state. Reload or eviction can reoffer a previously dismissed suggestion; another device is unaffected.

## Limits and preserved boundaries

Web unit tests mount the actual suggestion UI and actual Tiptap editor in jsdom, using controlled source/owner/connection atoms and zero-geometry Range stubs. They do not mount the full chat tree or prove browser layout, keyboard geometry, remote transport or Electron behavior. Mobile tests exercise its actual draft store, action adapter and native revision helpers with hermetic filesystem fixtures. They do not run UIKit, Android views, a compiled native bridge or an installed app. Existing native controlled-document code was inspected for revision rejection and controlled-update event suppression, not built or executed here.

Native snapshots describe JS-acknowledged events. Physical native events still in transit rely on the existing native controlled-document revision rejection; installed-client proof remains open. Suggestion-only local text mutations preserve current metadata, but do not redesign existing persistence sweeping or subsequent ordinary editing semantics.

No installation, prepare hook, dev server, Metro, browser/computer use, native/release build, real provider session, CLI handoff, auth flow, live/canonical/global operation, stage, commit or subdelegation was performed. No backend or RPC redesign was needed. B05's two Windows Claude fixture failures were neither rerun nor used as a waiver. Integrated web/desktop/iOS/Android, remote two-device behavior, native compatibility and broader parity remain for the authorized parent verification pass.
