## Token and cleanup design

Normal `startSession` and `recoverSessionForThread` acquire `startAdmission(threadId)` as their first effect. The controller methods are scoped, so that exact token remains registered across validation, registry work, per-thread queueing, startup and binding. No await or queue resumes by minting a replacement token.

Acquisition registers a service-issued object in the thread lane under the same mutation lock as reservations and deletion. The lane contains its original semaphore and a set of live admissions. `delete` revokes all admissions in that lane before inspecting the topic, including when no topic exists. It does not remove the lane or create a second semaphore. Revocation uses a WeakSet of tokens, not a permanent deleted-thread ID cache.

`withStart` receives the captured token and validates it before queueing, after acquiring the lane, and before returning. The final check covers the early verified-live adoption branch after its async work. Valid adoption still makes no destructive reservation and retains the existing lease.

`reserve` takes the original token rather than a thread ID. It validates before changing any owner and stores that token in the reservation. Producer reservation retrieval and `open` require it to remain registered and unrevoked, alongside the existing exact reservation/publisher checks. An old token cannot overwrite a newer same-publisher reservation or reopen ownership after deletion or scope release.

Scoped finalization releases the token and removes the lane only when its last admission finishes. It also clears an abandoned unopened reservation belonging to that token. It does not close a valid live lease when successful startup completes; later same-process writes continue through the existing lease fence. Admission counts are exposed only as a server-local inspection effect for deterministic cleanup tests, not in RPC DTOs.

No production adapter/model lifecycle, authorization, client, rendering, draft, title, platform or persistent schema behavior was otherwise changed. Mechanical existing fixture changes supply explicit tokens to the revised server-local API. The direct adapter fixture maps the controller validation error to its existing adapter error contract.
